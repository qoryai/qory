# qory 0.3.0

What the release changes, in the order the work is done, and why each change is in a
minor release rather than a patch. The input is the integration report from the first
harness repository that moved onto 0.2.x; the numbered requests in that report are
referred to as R1 to R6.

## Why 0.3.0

Three of the changes alter what a document a 0.2.x checkout already holds does:

- A `qory-stack.yaml` at a checkout root with no `extending` block composes today and is
  refused after this release (R3).
- The stack and the configuration get a `qory` key. A 0.2.x binary reading a document
  that carries it fails with "key `qory` is not one `qory-stack.yaml` reads", exit 2,
  before it can say the document wants a newer qory.
- `qory version` prints `0.2.0` from a release and `v0.2.0` from a source build. Both
  print the number without the `v` after this release, so a script that reads the first
  line sees one form.

Everything else is additive: a flag, a verb option, two report fields, two exit codes,
documentation. The format version stays `qory.ai/v1alpha1`, because every 0.2.x document
without a `qory` key still reads unchanged.

## Not in this release

- A version resolver in `install.sh`. Which release a runner installs stays the
  installer's choice; `QORY_VERSION=latest` already exists.

## 10. `only`, the parts a block may name, and `requires` (R6)

Added after the plan was written, on the decision that a stack configures per module
what the module contributes and that a module declares what its entries need.

- `exclude` and `only` on a stack module read the same keys: the seven kinds with a list
  of names, `instructions: true`, and `settings` and `env` as `true` or a list. Under
  `exclude` a named thing is left out. Under `only` a named thing is composed together
  with what it requires from the module, as the manifest declares it, transitively; a
  kind not named contributes no entry beyond those, a part not named is left out. An
  `exclude` beside an `only` names entries the `only` brought in, so a requirement can be
  taken from another module instead; it names no part and nothing the `only` names. A
  name that matches nothing the module ships is an error, as before. Every entry and part
  left out is recorded in the report's excludes, and a pulled entry records the entry
  that required it. Decided against letting a pulled entry yield to another module's:
  two modules contributing one entry stays a collision, resolved by an explicit line.
- `requires` in `qory-module.yaml` is a list of statements, one per entry: the singular
  key names the entry, the plural kinds list what it needs. A composed entry whose
  requirement is not composed fails the compose, naming the module that left it out or
  saying no module ships it.

  ```yaml
  requires:
    - skill: deploy
      commands: [ship]
      agents: [reviewer]
  ```

## 1. The `qory` key: a document states the qory it needs (R1)

### Where it goes

A top-level key, in both documents:

```yaml
# qory-stack.yaml, delivered by a harness repository
apiVersion: qory.ai/v1alpha1
qory: ">=0.3.0"
target: ...

# qory.yaml, a repository's own or the machine's
apiVersion: qory.ai/v1alpha1
qory: ">=0.3.0 <0.4.0"
harness: ...
```

The stack is where the key is expected. A harness repository delivers a stack to many
product repositories; the stack states the minimum, every client inherits it through
`extends`, and no client file changes when qory is upgraded on the runners. A product
repository may add its own `qory` key, and a machine file may too, but neither has to.

Under `extends`, the checkout's own `qory` key is read even though its `harness`, `git`
and `env` keys are not. The key can only tighten the range, so reading it takes nothing
away from the base's owner.

### Grammar

The value is a string of one or more comparators separated by spaces. A comparator is
one of `>=`, `>`, `<=`, `<`, `=` followed by a version, `0.3.0` or `v0.3.0`. Every
comparator must hold. There is no bare version: `qory: 0.3.0` is refused with the
message "`qory` is one or more comparators such as `>=0.3.0`", because a bare number
reads as a minimum to one person and as an exact pin to another.

Comparison uses `golang.org/x/mod/semver`, which orders prerelease and pseudo-versions
correctly. The dependency is one small pure-Go module.

### What is compared

The running binary's version, as `qory version --json` reports it (§2). Three cases:

| Build | Version compared | Checked |
|---|---|---|
| a release, `Version` set by ldflags | `0.3.0` | yes |
| a source build at a clean tagged commit; Go stamps the tag | `0.3.0` | yes |
| a source build between tags, or without VCS information; Go stamps a pseudo-version or nothing | none | no: the compose prints one row, `qory: 0.3.1-0.20260911-abc123, not checked against >=0.3.0`, and goes on |

A source build between tags is exempt because the person running it is developing qory,
usually against a stack that already says `>=` the version they are building. Refusing
that build would make every feature branch unusable until it is tagged. The `source`
field of `qory version --json` is what an installer reads to leave such a build alone.

### When it is checked

At the point each document is read, before any work:

- `harness compose`: every `qory.yaml` the configuration read, the stack, and the base
  stack once `extends` has fetched it. A base that fails the check is reported with the
  base's name and pin.
- `worktree add`: the same set, since it composes the worktree it makes.
- `config`: prints the effective range and the file it came from as a row; it does not
  refuse, because the verb exists to show what the files say.

`harness inspect` and `harness remove` read no document and do not check.

### The refusal

Exit status 5, `ExitVersion`. The message names the file, the range, and the running
version:

```
✗ qory-stack.yaml: this qory is 0.2.1, and the stack wants >=0.3.0
  install a qory in that range, or ask the stack's owner
```

For a base stack under `extends`: "the base stack `acme/core@a1b2c3` wants `>=0.3.0`".

### Code

- `internal/stack`: a `Constraint` type with `Parse(string)` and `Allows(version string)
  bool`, and `Stack.Qory Constraint` decoded from the `qory` key. `validate` refuses a
  string that does not parse.
- `internal/config`: `file.Qory` decoded the same way; `Config.Qory` holds the tightest
  set, and `origins` records each file that contributed one. `apply` reads the key
  regardless of the `machine` argument.
- `cmd`: a `versionError` type with the file, the range and the version; `ExitCode`
  maps it to 5. `runCompose` checks after `config.Load`, after `config.LoadStack` and
  after `compose.LoadBase`.
- `contracts/harness/v1`: `qory` in `stack.schema.json` and `config.schema.json` as a
  string with the comparator pattern; a fixture `qory-constraint-fails` with
  `expected/error.txt`; the key in the stack and configuration tables of the README.

## 2. `qory version --json` and a version a script can trust (R2)

### Output

```sh
$ qory version --json
{
  "version": "0.3.0",
  "commit": "a1b2c3d4e5f6",
  "dirty": false,
  "source": "release",
  "harnessFormat": "qory.ai/v1alpha1",
  "reportVersion": 1
}
```

- `version` is the number without the `v`, in every build that has one. A build with a
  pseudo-version reports the pseudo-version; a build with no version reports `""`.
- `commit` is `vcs.revision` from the build information, shortened to twelve
  characters, in a release build as well: goreleaser builds from a git checkout, so the
  stamp is there. If a snapshot build turns out to carry no stamp, goreleaser passes
  `-X github.com/qoryai/qory/cmd.Commit={{ .ShortCommit }}` beside `Version` and the
  ldflag wins. The field is `""` when the build carries neither.
- `dirty` is `vcs.modified`.
- `source` is `release` when `Version` was set by ldflags, else `source`. A `go install
  .` at a clean tag has the same `version` as the release and a different `source`, which
  is what the report's installer needs.
- `harnessFormat` is `stack.APIVersion`; `reportVersion` is `report.Version`.

The plain output prints the same fields as rows under the title, with the number in the
title without the `v` in both kinds of build. That is the one output change: today a
source build at a tag prints `v0.2.0` and a release prints `0.2.0`.

### Code

- `cmd/version.go`: split `version()` into a `build()` that returns a struct with the
  six fields, and keep `version()` as the string the title shows. Strip build metadata,
  the `+dirty` suffix Go 1.24 appends, before the pseudo-version test: today
  `v0.2.2-0.20260911000000-abc123456789+dirty` does not match the regex and prints as a
  version.
- `--json` writes the struct with `json.MarshalIndent` and a trailing newline.
- `CONTRIBUTING.md` § Releases: replace the sentence on what `qory version` reports.

## 3. The report records the qory that composed it (R1, R5)

Two fields in the report, absent when the build has no version:

```json
"qory": {"version": "0.3.0", "commit": "a1b2c3d4e5f6", "source": "release"}
```

`harness inspect` prints them as one row, `qory  0.3.0 a1b2c3d4e5f6 release`. The report
format version stays 1: a field a reader did not know is skipped by every JSON reader,
and the report's own `version` field is for a change that alters what an existing field
means.

The fields are what makes "CI and a laptop agree on which qory built the tree" checkable
without a pin: a diff of two reports shows the version beside the entries.

## 4. A root `qory-stack.yaml` with no `extending` block is refused (R3)

### The rule

When discovery finds `qory-stack.yaml` in the checkout root and the file declares no
`extending` block, the compose is refused with exit 2:

```
✗ qory-stack.yaml: a stack at a repository root is delivered to be extended, and this one
  declares no extending block
  a repository's own stack goes under harness in qory.yaml; qory setup repo writes one
```

The rule applies to discovery at the root only. These cases stay as they are:

- `-f path/qory-stack.yaml`: the person named the file.
- A `qory-stack.yaml` in an ancestor directory: it covers several checkouts and is meant
  to compose them directly.
- A root `qory-stack.yaml` with an `extending` block: the harness repository composing
  the stack it delivers, to test it.
- A stack reached through `extends`: it is checked by `stack.Extend`, which already
  refuses a base without the block.

### What has to move

`qory setup example` writes a root `qory-stack.yaml` without `extending`, so the example
would refuse itself. The example becomes a `qory.yaml` holding the same target and
modules under `harness`, which is also what the README's three steps show. The
example's `README.md` line about deleting the `exclude` lines names `qory.yaml`. The
example test and `cmd/setup_example.go` follow.

### Code

- `internal/config.DiscoverStack`: after `composeIn(root, false)` returns the stack file,
  load it and apply the rule; the error is an input error naming the file. The check
  lives in discovery rather than in `stack.Load`, so `-f` and the ancestor case are
  untouched by construction.
- A test in `cmd/compose_test.go` for the refusal, one for the ancestor case still
  composing, and one for `-f` on the same file.
- `contracts/harness/v1/README.md` § Three files: the row for `qory-stack.yaml` loses
  "a repository root" from its "Lives in" cell, and § Discovery states the rule.
- `examples/hello/qory-stack.yaml` becomes `examples/hello/qory.yaml`.

## 5. `qory harness compose --check` (R5)

### What it does

Composes in memory, renders into a scratch directory, and compares that render with the
home on disk. Nothing in the checkout changes. The result is one of:

| Result | Exit | Output |
|---|---|---|
| the home matches | 0 | `✓ up to date` and the module rows |
| a file or link differs, or is missing, or is extra | 6 | one row per path, then `✗ stale: run qory harness compose` |
| nothing is composed | 6 | `✗ nothing composed here` |
| the compose itself fails | as today | the same refusal as a compose |

A path row names the path under the home and one word for what differs: `changed`,
`missing`, `extra`, `target` for a symlink that points elsewhere. The instruction file, a
merged settings file and a merged MCP file are the cases the report asked for; every path
in the home is compared, so a skill added to a module and not yet composed is caught too.

`--check` implies `--dry-run` and refuses `--force`, which has nothing to replace. It
honours `--update` and the report's pins the way a compose does, so a check without
`--update` compares against the pinned commits and does not fetch. The exit status is
`ExitStale`, 6, so a CI gate tells a stale tree from a broken compose.

Two things `--check` does not compare, and says so in the command's help: the links from
the checkout into the home, and the report. A link that is missing is a foreign-path or
remove problem, not staleness; the report changes when the home does.

### Code

- `cmd/harness.go`: lift the first half of `runCompose`, from `locateAt` to
  `report.New`, into a `prepare(o composeOptions) (prepared, error)` that compose,
  `--dry-run` and `--check` share.
- `internal/render`: `Build` becomes a call to `BuildAt(res, stage, home, runtimes...)`,
  where `stage` is the directory written and `home` is the path the tree is addressed
  as, for `$QORY_HARNESS_HOME` and the relative links a runtime writes. `Build` stages
  at `home + ".tmp"` and renames; `--check` stages in `os.MkdirTemp` and never renames.
- `internal/render`: `Diff(want, have string) ([]Difference, error)` walks both trees
  with `filepath.WalkDir`, without following symlinks, and compares by path: a symlink by
  its target, a regular file by its bytes, anything else by its kind. The list is sorted
  by path.
- Tests: a compose, an edit to a module's `AGENTS.md`, a `--check` that exits 6 naming
  `AGENTS.md` and `claude/CLAUDE.md`; a second compose, a `--check` that exits 0; a
  `--check` in a checkout with no home.
- `docs/commands`: regenerate.

## 6. Exit statuses

| Status | Meaning |
|---|---|
| 0 | done |
| 1 | anything not listed: a file that could not be written, a git source that could not be fetched |
| 2 | a mistake in the input: the command line, the stack, a module, a fragment |
| 3 | a collision, printed with the excludes that resolve it |
| 4 | a path qory did not write standing where a link goes, which `--force` may replace |
| 5 | the running qory is outside the range a document's `qory` key declares |
| 6 | `--check`: the home no longer matches what the stack and modules say |

The table goes into the contract README, `cmd/harness.go` beside the constants, and the
`ExitCode` doc comment.

## 7. Documentation (R4 and the migration note)

### README: a section "The composed tree"

After "What you get". It says:

- The tree under `.qory/harness` is one real directory per runtime holding symlinks to
  the modules' files, plus the generated copies: `AGENTS.md`, each runtime's instruction
  file, settings and MCP files. Editing a module's file is live through the link.
  Editing a module's instruction section or settings fragment is not: the merged copy is
  generated, and `qory harness compose --check` says when it is behind.
- The checkout's own entries under `.claude` and its siblings are symlinks too, so a
  tool that walks the tree has to follow them. `find` needs `-L`. `grep -R` given a
  symlink as an operand without a trailing slash reads nothing with BSD grep on macOS
  and follows the link with GNU grep on Linux, with no error from either; give it
  `.claude/` with the slash, or `-R -L`. `rg` needs `--follow`.
- `git status` does not show the tree, because every path qory writes is listed in
  `.git/info/exclude`, which all worktrees of a repository share.

### CHANGELOG.md: the release, with an Upgrading section

The changelog at the repository root, in the Keep a Changelog shape, holds every release;
the 0.3.0 section starts with four upgrading lines:

- A stack or configuration with a `qory` key is refused by a 0.2.x binary as an unknown
  key, exit 2. Upgrade every machine before a delivered stack gains the key.
- A `qory-stack.yaml` at a repository root without `extending` is refused. Move its
  target and modules under `harness` in `qory.yaml`.
- `qory version` prints `0.3.0` from every kind of build. A script that read the `v`
  reads `qory version --json` instead.
- The instructions land at `.claude/CLAUDE.md` for Claude Code and at `AGENTS.md` in the
  home. A root `AGENTS.md` exists only for a runtime that reads one; add `any` to
  `target.runtime` to get the link at the root. A composer that wrote a root `AGENTS.md`
  had tests reading it; they read `.claude/CLAUDE.md` or add `any`.

### The contract

`contracts/harness/v1/README.md`: the `qory` key in both tables, the discovery rule from
§4, the exit table from §6, the `qory` field in the report section, and the composed
tree's shape in one paragraph that the README section links to.

### The release body

Goreleaser writes the commit list. The changelog section goes above it by hand, because
the person reading a release page does not open the repository.

## 8. Order of work

Each step is one pull request against `main`, with tests and documentation in the same
change. The order puts the change every other step reads on first.

1. §2 version: `build()`, `--json`, the metadata strip, the title without `v`.
2. §1 the `qory` key: parsing, the two readers, the checks, exit 5, schemas, fixture.
3. §3 the report fields.
4. §4 the root-stack rule and the example rewrite.
5. §5 `--check`: `prepare`, `BuildAt`, `Diff`, exit 6.
6. §7 documentation, `CHANGELOG.md` and `docs/commands` regenerated; `CONTRIBUTING.md` § Releases.
7. Tag `v0.3.0`, edit the release body, and send the harness repository's maintainers
   the upgrade section with a note that their stacks may now declare `qory: ">=0.3.0"`.

## 9. What is checked before the tag

```sh
go test ./...
gofmt -l .
go vet ./...
go run github.com/mgechev/revive@v1.16.0 -config revive.toml ./...
go run ./internal/gendocs docs/commands && git diff --exit-code docs/commands
goreleaser check
goreleaser build --snapshot --clean --single-target
./dist/qory_*/qory version --json          # source: release, commit set
```

And by hand in a checkout that extends a stack with `qory: ">=0.3.0"`:

```sh
qory hc                                     # composes
sed -i '' 's/0.3.0/0.9.0/' ../harness/stacks/app/qory-stack.yaml
qory hc; echo $?                            # 5, names the base and the range
qory hc --check; echo $?                    # 0 after a compose, 6 after editing a module's AGENTS.md
```
